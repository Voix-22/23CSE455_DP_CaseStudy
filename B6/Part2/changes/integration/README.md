# Integration of the four changes

Each change in `Change1` to `Change4` was written on its own branch, starting from the original code (`dfc61ab8`). `Part2/code/` holds all four together. This folder records how they were combined, one step per change, in folder order.

| Patch | From | To | Tests after the step |
|---|---|---|---|
| `step1_after_Change1.patch` | original code | code after Change1 (maintenance, State) | 233 total, 232 passed, 1 failed |
| `step2_after_Change2.patch` | code after Change1 | code after Change2 (vehicle categories, Factory Method) | 257 total, 256 passed, 1 failed |
| `step3_after_Change3.patch` | code after Change2 | code after Change3 (pricing policies, Strategy) | 279 total, 279 passed |
| `step4_after_Change4.patch` | code after Change3 | code after Change4 (notifications, Observer) = `Part2/code/` | 297 total, 297 passed |

All four runs: `dotnet test src/FlemanApi.Tests/FlemanApi.Tests.csproj`, .NET SDK 8.0.425, Windows 11, 2026-10-11. The full log of the last step is `Part2/code/test_result.txt`.

The one failure in steps 1 and 2 is `StaffServiceTests.ProcessReturnAsync_CreatesInvoiceHeaderAndDetails`. It also fails on the original code, because `StaffService` read `DateTime.Now`. Change3 gives `StaffService` an injected `TimeProvider` and the test a fixed clock, so it passes from step 3 on.

To rebuild `Part2/code/WanderCar_DotNet` from the original code, apply the four patches in order from the folder that contains `WanderCar_DotNet`:

```bash
git apply step1_after_Change1.patch
git apply step2_after_Change2.patch
git apply step3_after_Change3.patch
git apply step4_after_Change4.patch
```

The line numbers in `Part2/pattern_evaluation.csv` for "Code after ChangeN" refer to the code as it is after step N.

## Edits made only to make the changes work together

1. **`Program.cs`, step 3.** Change1 and Change3 each registered `TimeProvider.System`. The registration in the Change1 block was removed, so the clock is registered once (the "Clock abstraction" line from Change3).
2. **`MaintenanceFleetAvailabilityTests.cs`, step 3.** Change3 adds two constructor parameters to `StaffService` (`IPricingPolicySelector`, `TimeProvider`). The Change1 test that builds a `StaffService` passes them.
3. **`BookingServiceNotificationTests.cs`, step 4.** Change3 adds the constructor parameter `IPricingPolicySelector` to `BookingService`. The Change4 test that builds a `BookingService` passes a selector that returns `StandardPricingPolicy`, so the amounts it asserts stay the same.
4. **`FlemanDbContext.cs`, `Program.cs`, `BookingService.cs`, `BookingServiceTests.cs`.** Blocks added by different changes at the same place were kept one after the other. Apart from edit 1, no line of any change was dropped.
5. **Migrations.** `AddVehicleCategory` (Change2, 2026-10-08) runs before `AddMaintenanceSchedules` (Change1, 2026-10-10). The `AddMaintenanceSchedules` migration and the model snapshot were written by hand, not generated by `dotnet ef`. The snapshot was compared with the EF Core model using `IMigrationsModelDiffer` and showed no difference. The migration was not run against a MySQL server.
