## Smell observed but deliberately not fixed

The baseline calls `DateTime.Now` directly in several places: `StaffService.cs:91`, `StaffService.cs:124`, `StaffService.cs:149` and `BookingService.cs:126`. This is a hidden dependency on the system clock, which makes those paths impossible to test against a fixed time. The fix would be to inject `TimeProvider`, as this change does for its new code.

That refactoring is out of scope here, for two reasons:

- It would change the constructor signatures of `StaffService` and `BookingService`, which forces edits to the `SetUp` of existing tests.
- It touches files that CH04 (booking notifications) is likely to edit, which risks merge conflicts.

The new `MaintenanceService` avoids the smell from the start. The `TimeProvider` registration added in `Program.cs` means a later change could adopt the same approach for `StaffService` and `BookingService`.

### This smell already breaks a baseline test

`StaffServiceTests.ProcessReturnAsync_CreatesInvoiceHeaderAndDetails` **fails on the untouched baseline** (`dfc61ab8`) when it is run after early August 2026:

```
Failed ProcessReturnAsync_CreatesInvoiceHeaderAndDetails
  Expected result.AddonAmount to be 40.0, but found 690.0 (difference of 650).
Failed!  - Failed: 1, Passed: 182, Skipped: 0, Total: 183   (baseline, run 2026-10-08)
```

The cause is a mismatch between a fixed date and the live clock:

- The test fixes the handover at 2026-08-01 (`GivenHandedOverBooking`, `StaffServiceTests.cs:196`).
- `StaffService.ProcessReturnAsync` bills up to `DateTime.Now` (`StaffService.cs:124`).
- On 2026-10-08 that is 69 days × 10.0 = 690. The expected 40.0 is 4 days, which is only true on 4–5 Aug 2026.

CH03 does not touch this code, and rule 3 forbids editing the test. The failure therefore stays the same before and after CH03, and it should be recorded as a known baseline issue, not as a regression.
